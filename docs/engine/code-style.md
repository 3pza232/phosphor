# PHOSPHOR 代码规范

目标：低耦合、高可拓展；代码清晰整洁；注释精简专业；结构层次分明。
本规范同时约束人类开发者与 AI 协作者。有冲突时，**架构铁律 > 本规范 > 个人习惯**。

---

## 一、命名

| 对象 | 风格 | 示例 |
|------|------|------|
| 类型（class/struct/enum） | `PascalCase` | `Screen`, `Cartridge` |
| 函数 / 局部变量 | `snake_case` | `load_manifest`, `frame_count` |
| 成员变量 | `snake_case` 尾部下划线 | `screen_`, `cart_path_` |
| 常量 / 编译期值 | `kPascalCase` | `kDefaultFps`, `kMaxCarts` |
| 枚举值 | `snake_case` | `ShellMode::shelf`（与 Lua 侧的键名写法保持一致） |
| 宏（尽量避免） | `SCREAMING_SNAKE` | `PHOS_VERSION` |
| 文件 | `snake_case` | `cart_loader.hpp`, `screen.cpp` |

Lua 侧（卡带 API、示例、注解文件）一律 `snake_case`，与 C++ 侧保持一致。

## 二、文件组织

- 一个文件一个职责；文件名即主要类型的名字
- 头文件必须**自给自足**：单独被 include 即可编译，不依赖包含顺序
- 头文件使用 `#pragma once`
- include 顺序（组间空行）：本模块对应头文件 → **项目内其他模块** → 第三方库 → C++ 标准库。
  项目内头文件排在标准库之前，是为了让"这个模块依赖了谁"在文件开头一眼可见；
  规范与代码不一致时以小步对齐为准（要么改代码，要么改规范，不允许长期含糊）
- 源文件超过约 400 行时，应当自问是否该拆分（不是硬性上限，是自省信号）

## 三、注释哲学

- 注释回答**"为什么"**，不复述代码"是什么"。`i++ // 自增` 这类注释是负资产
- 公共接口在头文件用 doc 注释说明契约（参数、返回、错误行为），
  风格统一为 `///` 单行形式，保持精简：

```cpp
/// 将卡带加载进沙箱并执行 init。
/// 失败时返回错误信息且主机状态保持不变。
std::expected<void, std::string> load(const std::filesystem::path& cart);
```

- 实现文件内只在"不明显的取舍、绕过的坑、遗留的妥协"处留注释
- 允许且鼓励在特殊处理处标注 `NOTE:` / `HACK:` / `TODO(所有者):`
- **注释只描述"现在成立的约束"，不记录"改动过程与修复史"**。
  这类都要删掉或改写成约束：
  - ✗ `// 设备晚一步初始化就会丢掉声音（曾经的真实 bug）`
  - ✓ `// 音频必须先于开机动画就绪：boot 事件音与脚本的 phos.audio.* 都在第一秒内发生`
  - ✗ `// 这里原本漏了判空，导致崩溃，现已修复`
  - ✓ `// 控制通道可能未启动，command 队列此时为空`
  判断标准：新加入的协作者读到这条注释，需要知道"不能这么改"，还是只需要知道"以前错过"？
  后者属于提交信息与文档，不属于代码。
- 不用注释写日记（"2026-10-08 修改了 xxx"——这是 git 的事）

## 四、错误处理

- **外部输入一律不可信**：卡带、内容包、配置文件、控制通道消息——
  解析失败必须返回错误并安全降级，详见架构铁律"主机永不因卡带而死"
- 可恢复错误：返回 `std::expected`（或带错误信息的 `optional`），不抛异常穿过模块边界
- 异常仅用于"继续运行已无意义"的主机自身致命错误
- 卡带 Lua 错误：捕获 → 屏幕显示错误画面（红字报错也是主题体验的一部分）→ 可返回系统菜单
- 配置/内容包错误：静默回退默认 + 日志警告

## 五、C++ 使用约定

- 标准锁定 **C++17**，不使用更新特性（保持工具链兼容预期）
- RAII 管理一切资源（GL 对象、文件句柄、Lua state），禁止裸 `new/delete`
- 优先 `std::string_view` 传参只读字符串；所有权用 `unique_ptr`，共享需理由才能用 `shared_ptr`
- 不使用全局可变状态；跨模块共享的上下文集中在 `App` 并以引用注入
- 不用 `using namespace std;`（头文件中禁止一切 `using namespace`）
- 第三方头文件只允许出现在对应封装模块内（见 architecture.md 铁律 5）

## 六、复用与去硬编码（重要）

- **同语义数值只允许出现一次**：跨模块使用的常量置于 `core/defaults.hpp`；
  仅本模块使用的调参常量置于该文件的匿名命名空间；界面坐标集中在布局结构中
- **禁止复制粘贴式实现**：同一绘制/解析逻辑出现第二处时，先抽到共享原语
  （`core/ui`、`core/text`、`core/crt`）再被调用
- **界面绘制只用 `core/ui` 原语**：主机界面与卡带界面共用一套组件，
  不允许任何模块手搓边框、光标、进度条
- **产品信息（名称/版本）只从 `core/version.hpp` 取**，C++ 与 Lua 两侧一致
- **面向内容作者的文案/版本/路径应由 API 提供**（如 `phos.sys.version()`），
  内容脚本中出现硬编码的主机信息视为缺陷

## 七、耦合控制

- 模块间依赖只能"向下"，向上通信用回调（`std::function`）或接口注入
- 新模块引入新依赖方向前，先回到 `architecture.md` 更新分层图，再写代码
- "先直接用，以后再抽象"是允许的，但要在代码处留 `NOTE:` 标明临时性

## 八、Lua 侧约定（卡带与内容包）

- 卡带只通过 `phos.*` 与主机交互，禁止依赖未文档化的全局环境
- 内容包脚本（如开机动画）与卡带遵守同一套沙箱规则
- 文档与示例中的 Lua 代码必须能直接运行，不展示"伪代码"

## 九、提交与协作

- 提交信息格式：`<模块>: <动词开头的简述>`，如 `cart: 支持覆盖层 mod 文件查找`
- AI 生成的代码与人类代码同等对待：过规范、过审查、能编译、不留临时垃圾
- 文档与代码同步更新：改了行为就改对应 docs，不同步的 PR 视为未完成
