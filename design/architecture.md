# PHOSPHOR 架构规范

本文定义模块划分、依赖规则与目录结构。任何新代码的归属问题，先查本文。

---

## 一、分层与依赖铁律

```
┌─────────────────────────────────────────┐
│ shell    外壳层：待机界面 / 系统菜单 / 氛围装饰 │
├─────────────────────────────────────────┤
│ api      Lua 桥：Host API（卡带与主机插件的唯一入口）│
├──────────────┬──────────────┬───────────┤
│ cart         │ pack         │ agent     │
│ 卡带加载/沙箱  │ 内容包加载     │ 控制通道/CLI │
├──────────────┴──────────────┴───────────┤
│ core     核心层：App 主循环 / Screen 网格 / Input │
├──────────────┬──────────────┬───────────┤
│ render       │ audio        │ platform  │
│ OpenGL 渲染   │ miniaudio    │ OS 相关封装 │
└──────────────┴──────────────┴───────────┘
```

**依赖约束（本文件描述现状与设计意图，不是立法）：**

> 这些约束是**为了让改动便宜**：换渲染后端、换脚本引擎、把某个模块抽出去时，代价被限制在一个文件夹内。
> 判断标准是"哪种做法对项目更好"，不是"哪种做法更符合本文档"。若有更优设计，先改设计、再改本文档；
> 不允许的是**代码与本文档互相不一致**却没人发现。因此每条都写成可机械核查的形式。


1. **依赖方向向下**。唯一例外是**组装点**：`core/app.*` 必须知道所有层才能把它们接起来；
   其余 `core/` 单元（`screen` / `input` / `text` / `ui` / `audio` / `crt`…）不得 include 上层。
   跨层向上通信用回调/接口注入
2. **Lua 类型只出现在 `api/`、`cart/`、`pack/`、`devkit/`**：前两者是 Lua 的宿主（装载并运行脚本），
   第三个要核对注解与实现。`core/`、`render/`、`shell/`、`platform/` 出现 `sol.hpp` / `lua.hpp` 即违规
3. **OpenGL 只出现在 `render/` 与 `platform/window.cpp`**：前者是渲染后端，
   后者创建上下文并加载函数指针。其他模块出现 `glad.h` 即违规
4. `cart/`、`pack/`、`agent/` 三者互不依赖，都只依赖 `core/`；
   其中 `cart/`、`pack/` 还可以复用 `api/lua_value.hpp`（纯值读取：`{r,g,b}` → `Color`）——
   它们都要把脚本里的表读成引擎类型，规则必须唯一，否则同一份颜色在不同地方
   越界行为不一致
5. 第三方库 include 只允许出现在对应封装模块内，禁止散布全工程

动手前若发现某条约束已经不成立，有两种正确做法：**要么**改代码去满足它（当它确实更优），
**要么**改本章去记录新的现状（当新做法确实更好）——两种都可以，含糊其辞地留着不行。

## 二、模块职责

### core —— 核心层

| 单元 | 职责 |
|------|------|
| `App` | 应用生命周期与主循环（固定逻辑帧 + 渲染帧），模式分派 |
| `Screen` | 字符网格：游戏画面的**逻辑抽象**，与渲染完全解耦 |
| `Input` | 统一输入队列。物理键盘/手柄/agent 注入的输入在此汇流，消费者无从分辨来源 |
| `Audio` | 音频子系统：软件混音（波形/包络/扫频/噪声/音序器/采样），三层音量 |
| `ui` | 界面绘制原语：边框/菜单/进度条/正文/精灵/导航（主机与卡带共用） |
| `effects` | 仪式感动效：插卡电压闪烁、拔卡画面收缩 |
| `crt` | 显像管参数与档位（扫描线/孔径格栅/辉光/亮度补偿） |
| `text` | 文本工具：UTF-8 码点解码、显示宽度（全角算 2 格）、截断/折行/补齐/居中、删除事件约定 |
| `text_input` | 界面文本输入缓冲：过滤、退格（按码点）、限长、计数——输入进入界面的唯一入口 |
| `defaults` / `version` | 跨模块常量与产品信息的**单一来源** |

`Screen` 是本项目最重要的抽象：它是一个二维字符网格（字符 + 前景色 + 背景色）。
**渲染器只是网格的消费者之一**；文本导出器是另一个消费者（headless 模式下是唯一消费者）。
任何代码都不允许"往屏幕上画东西"，只能"往网格里写字"。

### render —— 渲染层

读取 `Screen` 网格 → 字体图集采样 → 全屏 CRT 后处理（扫描线/辉光/暗角/畸变）。
后处理参数来自当前激活的 palette 内容包，渲染器自身不硬编码任何"风格数值"。

### api —— Lua 桥

将 core/audio 的能力封装为 `phos.*` API 暴露给 Lua。职责包括：
沙箱环境构造（卡带 Lua 无法访问 os/io 的危险面）、API 注册表
（表结构开放注册，为主机插件预留扩展口）、卡带错误的捕获与上报。

### cart —— 卡带系统

`.phos` 文件读取（zip）、manifest 校验、Lua 沙箱装配、卡带生命周期管理、
存档读写（磁带码导出/导入）、覆盖层 Mod 的文件查找重定向。

### pack —— 内容包系统

统一的内容包加载器：皮肤/开机动画/配色/音效/字体共用同一套
"manifest 校验 → 资源装载 → 回退默认"机制。卡带加载器也是它的近亲，
但卡带因生命周期复杂而独立成 `cart/`。

### render/font —— 字体链与全角字符

**字体链**（`FontChain`）封装 stb_truetype：在生效的字体方案（`theme/font/<方案>/`，
方案名取自配置 `font`，缺省 `default`）内按 `font.* → font-*` 依次取第一个含该字形的字体。
第三方头只出现在 `render/font.cpp` 内，
接口不暴露 stbtt 类型；`STB_TRUETYPE_IMPLEMENTATION` 也只在那个 TU 定义
（stb 的实现函数默认 `static`，放在别处会链接不到）。

**全角字符占两格**靠 `Cell::cols` 表达：`2` 是头格、`0` 是续格（自身无字形）。
渲染器跳过续格（整格由左邻的宽字形覆盖），`to_text()` 也不为续格产出字符，
于是"中文"在文本里保持相邻。

两条渲染路径共用同一套度量：

| 路径 | 字形来源 | 用途 |
|------|----------|------|
| `render/renderer.cpp`（GL） | ASCII 一次打包进静态区；其余码位**按需**光栅化并装入图集动态区（行式装箱，满了就告警并退占位符） | 窗口显示 |
| `render/screen_image.cpp`（CPU） | 逐格临场光栅化（同样的字体链） | 截图 |

> **画面模型**：字符网格 80×45 格 × 16px（= 1280×720），每格一个字形 + 真彩前景/背景
> （颜色不是瓶颈，分辨率与字形才是）；CRT 后处理作用于整帧。若要"比字符更细"的颗粒
> （瓦片/像素层），设计草案与工作量见 `roadmap.md` 第六节。

### core/log —— 主机日志

`--log <file>` 时把主机事件写盘（时间戳 + 逻辑帧号），与 agent 的控制命令落在同一条
时间线上；`info` 只进文件，`warn`/`error` 同时打 stderr（不指定 `--log` 时行为与以往一致）。
卡带的 `phos.sys.log()` 也汇入同一文件。

### devkit —— 卡带工具链

`--pack`（目录 → `.phos`，含 manifest 与入口校验）、`--new`（从模板生成骨架）。
与运行时共用同一套卡带探测逻辑（`cart_files` + `parse_manifest`），
避免"打包器认为合法、运行时却加载失败"的分叉。

### agent —— 机器接口

命令行参数解析（headless / dump-screen / screenshot / frames 等）、
调试仪表盘（ImGui）、本地控制通道（NDJSON over TCP）、日志落盘（`--log`）。
本模块只**读取状态与注入输入**，不产生任何游戏逻辑副作用。

### shell —— 外壳层

开机动画播放、待机画面、卡带架、系统菜单（Esc 呼出）、机身装饰渲染。
shell 与卡带**地位平等**——它是主机自带的"系统卡带"，通过同一套 Screen/API 能力工作。

为保持文件职责单一，外壳按视图拆分：

| 文件 | 职责 |
|------|------|
| `shell.cpp` | 外壳状态、各模式的输入意图、机身与公共装饰（标题栏 / 页脚） |
| `shell/layout.hpp` | 全机统一的外壳布局常量（`ShellLayout`）：各模块共用一套边距，谁也不另写一份 |
| `shell/shelf_view.cpp` | 卡带架两种样式的渲染（列表 / 视窗轮播） |
| `shell/settings_view.cpp` | 设置项的布局、分区与取值显示 |
| `shell/tape_view.cpp` | 磁带码界面：状态、输入、滚动与绘制（`tape::ScreenState`），外壳只给它数据与画外框 |
| `shell/boot_view.cpp` | 没有启动动画包时的内置自检屏 |

### audio —— 音频层

miniaudio 封装：软件混音（波形 / 包络 / 扫频 / 噪声）、采样播放、曲式化音序器，
三层音量（主 / 音乐 / 音效）。音源数据可来自音效内容包。

**线程模型（理解"为什么没有锁"的关键）**：

- **主线程只入队**：一切发声请求（合成音 / 音符 / 采样 / 采样登记 / 曲目 / 停止）都写进
  一个 SPSC 请求队列，`head` 由主线程写、`tail` 由音频线程写，靠原子发布。
  采样数据本身也走这条路**移交所有权**：解码在主机侧完成，此后样本只由音频线程持有，
  回调侧因此不需要锁，也不会与主机侧的登记撞车。
  主线程**绝不触碰声部表**——音频回调偶尔跑得久，也只是晚几十毫秒出声，
  游戏循环不会为"发一个音"而等待。
- **音频线程是声部表的唯一写入者**：每块混音开始前整批取走请求并落地；
  音序器（推进乐段、触发音符）同样跑在音频线程上，与请求共用一套落地逻辑。
- **队列满则丢弃并计数**（`dropped_requests()`）：宁可少一声，也不阻塞游戏循环。
- 跨线程可读的状态（是否在播、乐段序号、活跃声部数、各层音量）一律用原子量，
  状态查询读到的是快照，可能落后一块混音。

### platform —— 平台层

窗口（GLFW）、文件对话框、路径处理等 OS 相关的唯一聚集地。

## 三、仓库目录结构

```
phosphor/
├── CMakeLists.txt
├── .gitignore             # 忽略构建产物与运行期生成物
├── docs/                  # 设计文档（你正在读的这些）
├── extern/                # 全部第三方依赖（glfw/glad/lua/sol2/stb/miniaudio/miniz）
├── src/                   # 主机源码
│   ├── main.cpp
│   ├── agent/  api/  cart/  core/  devkit/  pack/  platform/  render/  shell/
├── package/               # 程序包内容源（构建时整份复制到输出目录）
│   ├── carts/             # 演示卡带（snake / life / bricks）
│   ├── theme/             # 出厂内容包：skin / boot / palette / sound
│   ├── devkit/            # 模板卡带 / phos.lua 注解 / 说明
│   ├── mods/  saves/      # 覆盖层与存档目录（各带 README 引导）
│   └── README.txt
├── tools/                 # 主机侧验证与演示脚本（Python）
└── build/                 # 构建输出（同时就是可直接运行的程序包目录）
```

## 三之二、构建目录（`build/`）里有什么

`build/` 同时承担两个角色：CMake 的输出目录 + 可直接运行的**程序包目录**。
看到"里面东西很杂"是正常的，分四类看就清楚了：

| 类别 | 内容 | 能不能删 |
|------|------|----------|
| CMake 产物 | `CMakeCache.txt`、`CMakeFiles/`、`Makefile`、`cmake_install.cmake`、`compile_commands.json`、`lib*.a`、`phosphor.exe` | 删了要重新构建 |
| 构建时复制 | `carts/`、`theme/`、`mods/`、`devkit/`、`README.txt` —— 每次构建从 `package/` 覆盖而来 | 可删，下次构建自动回来 |
| 运行期生成 | `config.json`（机台设置）、`saves/*.sav`（你的存档） | **别删**（删了设置和纪录就没了） |
| 临时物 | `*.log`、`dist/`（打包产物）、`shots/`、`saves/demo/` | 随便删，`tools/clean.py` 一键清 |

两条容易踩的规则：

- **不要直接改 `build/` 下的卡带与内容包**——它们与 `package/` 同名，下次构建就被覆盖。
  要长期保留的改动请改 `package/` 下的同名文件（`--new` 在 `build/carts/` 新建的目录不会被删，
  但它不在源码里，换机器就没了）。
- 程序在**哪个目录运行，就在哪个目录留下** `config.json` 与 `saves/`；
  自动化跑测试或演示时用 `--save-dir` 指到临时目录，别动玩家存档（`tools/` 下的脚本已经这么做）。

## 四、程序包（分发形态）结构

构建产物的目录形态。**除 exe 与 dll 外的一切都是用户可触碰的**：

```
PHOSPHOR/
├── phosphor.exe
├── （运行所需 dll）
├── theme/                 # 内容区（出厂默认包随发行版提供），每个子文件夹有 README.txt 引导
│   ├── skin/     外壳皮肤
│   ├── boot/     启动动画
│   ├── palette/  显像管配色与 CRT 参数
│   ├── sound/    音效包
│   └── font/     字体方案（default 方案含中文思源黑体）
├── carts/                 # 卡带存放处（卡带架扫描这里）
├── mods/                  # 覆盖层 Mod
├── saves/                 # 存档
└── config.json            # 机台配置（激活的主题选择、屏幕参数等）
```

资源查找顺序：`theme/ 内容包 → 内置硬编码兜底`（各类型自带默认包，
磁盘上一个都没有也能开机）。任何一级缺失都安静降级并留日志，绝不报错退出。

## 五、构建约定

- CMake ≥ 3.28，编译器无关；主力工具链为 **GCC 13+ (MinGW-w64)**，
  代码禁止任何编译器私有扩展（如 `__declspec`），保持 GCC/Clang/MSVC 皆可构建
- C++17 标准锁定（`CXX_STANDARD_REQUIRED`）
- 开启 `CMAKE_EXPORT_COMPILE_COMMANDS`，供 clangd 提供 IDE 智能
- 第三方依赖一律从 `extern/` 引用（GLFW 使用 `lib-mingw-w64` 预编译库），不使用系统级安装
- Lua 源码作为静态库目标编译（排除 `lua.c` / `luac.c`）
- 构建后将 `package/` 整份拷贝到输出目录（内容文件改动无需重新链接）
